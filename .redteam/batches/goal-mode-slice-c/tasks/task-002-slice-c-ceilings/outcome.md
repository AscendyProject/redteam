# Outcome — Slice C: hard ceilings enforcement + goal-level done-criterion

## Goal
When a batch declares an optional `goal.json` manifest, the orchestrator validates
and **enforces** `ceilings.max_tasks` at manifest-load time (fail-closed, before
any task state is seeded or any task runs) and, after the layered run, surfaces a
goal-level done-criterion — `GOAL COMPLETE` only when every manifest task ended
`done`, otherwise `GOAL INCOMPLETE` naming **every** manifest task whose result
was not `done`. The goal-level status is produced **in the same single pass as
the per-task results** (no second disk read of `goal.json`), exposed through a
new `_run_batch` API that `process_batch` and `_run_pipeline` both go through, so
it is unit-testable — not only printed. Absent `goal.json`, behavior is
byte-for-byte unchanged. No auto-merge, no gate change.

## Done-when
- [ ] `bash .redteam/scripts/verify.sh` passes (ruff check + ruff format --check + full pytest), with `test_agents_generic_prompts.py`, `test_install.py`, `test_goal_manifest_validation.py`, and `test_goal_dag_scheduler.py` green.
- [ ] `_load_goal_manifest` (`.redteam/workflows/orchestrator.py:754`) validates `ceilings.max_tasks` **shape** when the key is present: it must be an integer `>= 1`. `0`, negative integers, non-integer values (`str`, `float`, `list`, `dict`, `None`), and `bool` (both `True` and `False`) each cause `_load_goal_manifest` to raise `ValueError`. `bool` is rejected **before** the integer-range check (the `isinstance(True, int)` trap). The raise flows through Slice A's existing fail-closed handler at `.redteam/workflows/orchestrator.py:1607-1613` — no second, weaker abort path is introduced.
- [ ] `_load_goal_manifest` **enforces** the ceiling when shape-valid: if `len(tasks) > ceilings.max_tasks`, it raises `ValueError` whose message names both the actual task count and the declared ceiling. The abort flows through the same Slice A handler — no task state is seeded and no task is run.
- [ ] `len(tasks) == ceilings.max_tasks` is accepted (boundary): the batch proceeds through the layered scheduler exactly as under Slice A.
- [ ] `ceilings` absent, or `ceilings` present without a `max_tasks` key, imposes **no task-count bound** — the batch runs exactly as under Slice A.
- [ ] **v1 stance pinned: unknown `ceilings.*` keys are tolerate-and-ignore.** Keys other than `max_tasks` (explicitly including token-budget and wall-clock-budget shaped keys, e.g. `max_cost`, `max_tokens`, `max_wall_seconds`) MUST NOT abort the batch. They are accepted opaquely and not enforced in this slice. Strict-reject is explicitly **not** chosen for v1; this is a forward-compat lever for Slice B / #92.
- [ ] A new module-level structured value `GoalStatus` is added in `.redteam/workflows/orchestrator.py` (a `@dataclass(frozen=True)` or `typing.NamedTuple` — both are stdlib; pick whichever matches surrounding orchestrator style) with exactly the attributes `complete: bool`, `done_count: int`, `total: int`, `incomplete_ids: list[str] | tuple[str, ...]`. No other attributes. (The field is named `incomplete_ids`, not `blocked_ids`, because its membership rule is the negative of `done` — see next item — and the previous `blocked_ids` name would mislabel results like `"no_input_md"` and the `f"error: {e!r}"` prefix strings.)
- [ ] A new pure helper `_compute_goal_status(results: dict[str, str], manifest_task_ids: list[str]) -> GoalStatus` is added at module scope in `.redteam/workflows/orchestrator.py`. It is side-effect free, reads no files, makes no subprocess calls, and computes:
  - `total == len(manifest_task_ids)`;
  - `done_count == sum(1 for id in manifest_task_ids if results.get(id) == "done")`;
  - `complete == True` iff every ID in `manifest_task_ids` has `results.get(id) == "done"`;
  - `incomplete_ids` lists **every** ID in `manifest_task_ids` for which `results.get(id) != "done"`, in the order they appear in `manifest_task_ids` (i.e. `_topo_layers` dispatch order). This explicitly includes — without enumerating exhaustively — the `TaskOutcome` strings `"blocked_on_human_gate"`, `"blocked_on_dependency"`, `"deferred"`, `"error"`, the `_run_one_task` shape `"no_input_md"`, any `f"error: {e!r}"` exception-prefixed string produced by `_run_one_task` at `.redteam/workflows/orchestrator.py:1590-1591`, any `f"error: {exc!r}"` validation-prefixed string produced by the Slice A fail-closed handler at `.redteam/workflows/orchestrator.py:1607-1613`, **and any future non-`"done"` result string the scheduler may emit**. Membership is determined solely by inequality with the literal `"done"`. The function is directly unit-testable by calling it with synthesized inputs.
- [ ] A new function `_run_batch(batch_dir: Path) -> tuple[dict[str, str], GoalStatus | None]` is added in `.redteam/workflows/orchestrator.py`. It contains the **real batch worker**: it loads `goal.json` **once** via `_load_goal_manifest`, runs the layered scheduler, and (for manifest mode) computes the goal-status by calling `_compute_goal_status(results, manifest_task_ids)` where `manifest_task_ids` is the flattened `_topo_layers(deps)` dispatch order **constructed from the in-memory `deps` map**. `_run_batch` never re-reads `goal.json` or any per-task state from disk to derive the status.
- [ ] `_run_batch` second-element semantics:
  - **Flat mode** (no `goal.json` at `batch_dir/goal.json`): `(results, None)`.
  - **Manifest-aborted** (`goal.json` exists but `_load_goal_manifest` raises — Slice A causes OR the new ceiling causes): `(results, None)` — `results` is the existing `error: ...` dict produced by the Slice A fail-closed handler.
  - **Manifest-ran** (`goal.json` exists and validates): `(results, GoalStatus(...))` populated from the in-memory results+deps of this same pass.
- [ ] `process_batch(batch_dir: Path) -> dict[str, str]` becomes a **thin backward-compatible wrapper**: its body is `return _run_batch(batch_dir)[0]`. The signature, the return type (`dict[str, str]`), and the per-key value contract are preserved verbatim. Every existing caller and every Slice A test (`results == {"task-a": "done", ...}`-style assertions at `test_goal_manifest_validation.py:247-253` and `test_goal_dag_scheduler.py:83-87`) continues to pass without modification.
- [ ] `_run_pipeline` (`.redteam/workflows/orchestrator.py:1689`) calls **`_run_batch` directly** (not `process_batch`) to obtain both the results dict and the optional `GoalStatus` in a single pass. The previously-existing `results = process_batch(batch_dir)` line is replaced by `results, goal_status = _run_batch(batch_dir)`. `_run_pipeline` does **not** re-load `goal.json` and does **not** call `_load_goal_manifest` a second time.
- [ ] `_run_pipeline` emits a goal-level status line under exactly the following three surfaces, driven solely by `goal_status`:
  - **Flat mode** (`goal_status is None` because no `goal.json`): **no** goal-level line is emitted. Stdout/stderr for a given set of per-task results is byte-for-byte identical to today's flat-mode output.
  - **Manifest-aborted** (`goal_status is None` because validation raised): **no** `GOAL COMPLETE` line AND **no** `GOAL INCOMPLETE` line is emitted. The existing per-task `error: ...` summary lines remain the only surface; conflating a validation failure with a completed-but-incomplete scheduler pass is forbidden.
  - **Manifest-ran** (`goal_status` is a `GoalStatus`): exactly one goal-level line is emitted, printed **after** the existing per-task / blocked / deferred / dep-blocked summary lines. On `goal_status.complete is True` it matches the regex `^GOAL COMPLETE — draft-PR stack ready for human review \(\d+/\d+ tasks done; not merged\)$` (rendered with `done_count`/`total`). On `goal_status.complete is False` it matches `^GOAL INCOMPLETE — \d+/\d+ done; incomplete: <id>(?:, <id>)*$` where the IDs are exactly `goal_status.incomplete_ids` in order. The literal label `incomplete:` (not `blocked/deferred:`) is required, so the surface text and the membership rule agree.
- [ ] Stdlib-only: no new non-stdlib imports are added to `orchestrator.py` or any helper module. No engine project-/stack-specific fingerprints are introduced (the engine remains generic).
- [ ] Slice A invariants are preserved verbatim: `_ensure_task_branch`, the `base_branch` pin, the freeze guard, `pinned_base_branch`, the single-parent forest rule, `_topo_layers`, and the `blocked_on_dependency` cascade are not modified by this slice. The layered-run body inside `_run_batch` is the existing `process_batch` manifest-mode body, moved — not rewritten.

## Out of scope
- The goal → task **decomposer** and decomposition review (Slice B).
- **Token / wall-clock ceilings enforcement** — keys other than `max_tasks` are tolerate-and-ignore in v1; no semantics are attached to them in this slice.
- Strict-reject for unknown `ceilings.*` keys (explicitly **not** chosen for v1; documented in Done-when).
- The per-round reviewer cost work in #92 Proposals 1–4.
- Any change to `_ensure_task_branch`, the `base_branch` pin, the freeze guard, `pinned_base_branch`, `_topo_layers`, or the `blocked_on_dependency` cascade.
- Auto-merge, auto-retarget of stacked PRs, or any change to `GATE_SENTINELS` / `MANUAL_PHASE_SENTINELS`. Goal-complete is **reported only**, never a merge trigger.
- Multi-parent DAGs and integration branches.
- Adding a `[goal]` or `[ceilings]` config surface to `config.toml` — the manifest itself is the surface.
- Memoizing manifest reads, caching the load result across calls, or moving validation out of `_load_goal_manifest`.
- Adding a `GOAL ABORTED` status line for the manifest-aborted surface (explicitly suppressed in v1).
- Changing `process_batch`'s signature or `dict[str, str]` return type (it stays a thin wrapper over `_run_batch[0]`); adding a `process_batch_v2`.
- A second disk read of `goal.json` (or any per-task state file) anywhere on the goal-status path — `_run_pipeline` consumes the `GoalStatus` returned from the same `_run_batch` call.
- Categorizing `incomplete_ids` by reason (e.g. a separate `error_ids` / `blocked_ids` / `deferred_ids` split). The single `incomplete_ids` field is the whole surface; finer-grained categorization is a follow-up if anyone asks for it.

## Risks
- **`_run_batch` is the new real worker; `process_batch` is a thin wrapper.** Goal-level information is exposed in-band via `_run_batch`'s second tuple element, satisfying the brief's "make the determination available from `process_batch`, unit-testable, not only printed" requirement, while the `dict[str, str]` `process_batch` contract is preserved verbatim. The alternative — widening `process_batch`'s return type — would break every Slice A test and every existing caller; the wrapper split avoids that. If a future slice (e.g. Slice B's decomposer integration) wants the status surfaced through `process_batch` itself, that is a separately-reviewed widening, out of scope here.
- **Single-pass invariant.** `_run_batch` must compute the `GoalStatus` from its in-memory `results` and `deps` — not by re-reading `goal.json` or any task-state file from disk. The brief's Risks note ("read the SAME per-task result map the scheduler already produces — don't re-derive task status from disk") pins this. A previously-considered `_run_pipeline` re-load of `goal.json` is therefore not part of this plan.
- **Aborted-manifest surface emits no goal-level line.** A validation failure is a different failure mode from a completed-but-incomplete scheduler pass; conflating them would mask the abort. `_run_batch` signals this by returning `None` as the second element on aborted-manifest, and `_run_pipeline` suppresses the goal line whenever the second element is `None`. A dedicated `GOAL ABORTED` line is a possible follow-up but is explicitly out of scope.
- **Unknown `ceilings.*` keys are tolerate-and-ignore.** Strict-reject was rejected because the brief itself flags token/wall-clock keys as out of scope for enforcement; rejecting them would lock out Slice B / #92 work that may add them. Tests assert the tolerate behavior with concrete token/wall-clock shaped key names. (Slice A's `test_valid_manifest_parses_ok` already exercises `ceilings: {"max_cost": 10}` and must stay green.)
- **`incomplete_ids` semantics are "every non-`done`", not a fixed enum.** This is a deliberate widening of the brief's example wording ("blocked/deferred: <task ids>"), driven by the actual `_run_one_task` contract: that function returns `"no_input_md"` (no `state.json`/`input.md` at `.redteam/workflows/orchestrator.py:1584-1585`) and `f"error: {e!r}"` (exception capture at `.redteam/workflows/orchestrator.py:1590-1591`) — neither matches a fixed `{"blocked_on_dependency", "deferred", "error", "blocked_on_human_gate"}` set. A fixed-set rule would silently drop those tasks from the incomplete surface, which is exactly the failure the brief warns against ("the incomplete surface names the offending task(s)"). The chosen rule — membership iff `results.get(id) != "done"` — keeps the surface honest under arbitrary future `_run_one_task` return strings. The displayed label is `incomplete:` rather than `blocked/deferred:` so the surface text matches the membership rule.
- **Boolean-is-an-int trap in Python.** `isinstance(True, int)` is `True`. The validation rejects `bool` explicitly **before** the integer-range check; the test-author phase writes both `True` and `False` rejection cases.
- **`GoalStatus` representation is left open between `@dataclass(frozen=True)` and `typing.NamedTuple`** — both are stdlib and both match patterns already in the repo (`config.py` uses frozen dataclasses; `phase_runners/_base.py` and `adapters/_protocol.py` use `TypedDict`). The attribute contract (`complete`, `done_count`, `total`, `incomplete_ids`) is pinned; the implementer picks the concrete form to match surrounding style. `TypedDict` is **not** acceptable here — the brief language ("compute … goal-complete") implies attribute access, and a dict shape would weaken the type guarantee at call sites.
- **Umbrella design doc still absent on this branch.** `docs/decisions/2026-06-27-goal-mode-design.md` is cited in the brief but not present in the repo (confirmed via Glob; only `2026-06-17-reviewer-transport-and-subagent.md` exists under `.redteam/docs/decisions/`). The design doc lives on the not-yet-merged PR #110 branch and is not required to land in this PR; the brief is authoritative for Slice C. If the design doc materially diverges from this brief when it does land, that becomes a follow-up reconciliation, not a blocker for this slice.
